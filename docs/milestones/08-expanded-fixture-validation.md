# 扩展 Windows 样本与写入压力验收

日期：2026-09-14。继续调查小文件正文是否能从旧日志补回，并扩大实际删除测试。新增可重复运行的扩展样本、删除后追加写入阶段和按场景/大小统计的验证报告。本轮没有新增驻留日志数据导出：实际材料尚未提供足够正文证据。

## 新增开发

- `New-RecoveryFixture.ps1 -Profile expanded` 创建 36 个原件、34 个删除目标。新增随机内容覆盖 0、1、63、127、255、383、511、639、767、1023、2049、4095、4096、4097、32769 字节，包含二进制、中文长路径及小文件改写、截短、重命名。原件在最后一次编辑后保存到宿主盘；恢复引擎不会读取它们。
- `-WritePressureMiB 1..64` 可追加第五个阶段，写入 64 个 257 字节小文件和指定数量的 1 MiB 文件。所有操作只发生于脚本刚创建、逐步核对身份的 128 MiB VHD。工作量和阶段摘要保存为独立证据；批量字节数不是覆盖比例。
- `Invoke-RecoveryValidation.ps1` 转交配置，并支持 `-DeepPng -DeepLog`。默认配置仍是原四阶段。验证器拒绝压力清单、阶段、原件或目标计数不一致的材料。
- 验收摘要增加 `by_scenario` 和 `by_size_bytes`，只统计重新读取导出内容后匹配的独立目标。空文件是单独的大小组，追加文件不是恢复目标，跨阶段重复目标仍不作为独立文件数。

## 真实实验

两组均在本机 Windows 11 管理员会话独立创建，原件及日志各自生成，NTFS 起始扇区为 128。每组先直接删除 26 个文件，再将另 8 个文件移入并清空该虚拟盘的回收站。前四阶段冻结后才追加写入。两个 VHD 均成功卸载，操作前后已有磁盘身份清单一致。

| 阶段 | 删除目标 | 4 MiB 组完整内容 / 原路径 | 32 MiB 组完整内容 / 原路径 |
| --- | ---: | ---: | ---: |
| 删除前 | 0 | 0 / 0 | 0 / 0 |
| 直接删除后 | 26 | 26 / 26 | 26 / 26 |
| 另 8 个文件移入回收站后 | 26 | 20 / 20 | 20 / 20 |
| 清空回收站后 | 34 | 28 / 28 | 28 / 28 |
| 追加写入后 | 34 | 2 / 0 | 2 / 0 |

两组同时启用 PNG 和旧日志扫描，整轮均为 `incomplete`、退出码 1。追加写入后剩下的两份是按内容找到的 PNG，原路径未知。两组使用相同生成程序和主机；不是跨平台统计，也不能由这两个数据点推断任何介质上的覆盖曲线。

材料根目录为 `artifacts/resident-recovery-acceptance/`：

- `pressure-4-b3c77301d81c42e0bff75b35669fc2a9/ntfs-fixture-e863105528d044358519fe5d7e5b88c1/`：4 MiB 组。
- `pressure-32-ec804471ae5d4ac4b2a6740b9d640739/ntfs-fixture-4c66dcf21c024793bcd4b3f5400a575f/`：32 MiB 组。
- `baseline-expanded/`、`expanded-32/`：开发环境初验；最终包内复验另存 `package-expanded-4/`、`package-expanded-32/`。

## 小文件调查结论

4 MiB 组在清空回收站后，缺失的直接删除小文件依然没有可用于补回完整正文的日志证据。对受影响镜像提取 `$MFT`、`$LogFile` 并校验更新序列后，检查已解析事务的 redo/undo 内容及日志页中的正文；改写、截短和长名称场景也没有补出完整的驻留用户正文。1 字节内容会在无关元数据中大量命中，不能建立文件关联。

`resident-evidence.json` 保存探索结果，`inspect-resident.py` 仅为人工诊断使用独立原件搜索正文，不属于恢复引擎，也不能作为由原件反推恢复结果的实现。原始字节搜索还会受 NTFS 扇区更新序列影响，未命中本身不足以断言整个卷上的内容不存在。

继续拒绝从创建时的空数据属性导出所谓成功的小文件。此前冻结基本样本的 79 字节 `中文.txt` 仍未恢复，`large-note.txt` 仍只保留 11,704 字节片段；原基本样本完整内容与原路径均保持 6/8。本轮扩大了已实测边界，没有声称提高这两份缺失文件的完整恢复率。
