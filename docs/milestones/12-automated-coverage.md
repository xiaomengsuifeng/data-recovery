## 测试发现并修复的问题

1. **坏区零填充遇到短写会残留旧字节。** 续采中的 pending 区域可能保留未发布的旧数据。原实现只调用一次零写入，在目标只接收部分数据时仍记录坏区完成。现统一循环写满正常数据和坏区占位，fsync 后再发布进度。回归先在 pending 区域写入旧字节，将每次目标写入限制到 3 字节，再使源读取失败，最终逐字节确认全部清零；坏区仍不算恢复数据。
2. **扫描断点的 `backend: null` 导致异常退出。** 现在先验证字段类型，再比较 TSK 版本；CLI 返回可读错误和退出码 2，不生成完成会话。损坏 JSON、选项、源身份、游标、版本和阶段还有组合回归。

新增测试入口对父测试、参数子用例、setup 失败及跳过分别记录。任何跳过都会使报告为 `incomplete`；无测试、失败或覆盖率不达门槛返回非零，严格模式也会因跳过失败。CI 上传日志和 HTML，远端工作流是否通过需查看实际运行结果。

## 交付和复验边界

源码版本与候选便携包更新为 `0.3.0rc2`，旧 rc1 包保留。新包名为 `dist/ShiHui-0.3.0rc2-windows-x64.zip`。Windows 包内运行时为 Python 3.13.12，使用固定的 Qt/TSK 归档；coverage 仅为开发测试依赖，不加入普通恢复运行时。

包构建后的结果保存到本轮证据目录：`package-build.json` 记录 ZIP 大小和 SHA-256，`package-check.log` 检查清单及 Qt/TSK 启动，`package-pe.json` 检查 PE 依赖，`package-ntfs/`、`package-extended/`、`package-exfat-fixture/` 记录实际包内引擎验收，`package-validation.json` 汇总目录、源码与 ZIP 字节一致性。最终包的 SHA-256 也保存在同名 `.zip.sha256` 文件，避免将包摘要写回包内造成循环依赖。

扫描断点要求软件版本一致，rc1 的 `scan-progress.json` 应用原 rc1 包继续，或用 rc2 重新扫描；不要修改进度文件伪装版本。已完成的扫描记录仍可打开，采集进度格式保持 version 1。
