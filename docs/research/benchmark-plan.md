# 数据恢复竞品对照测试方案

调研日期：2026-09-12。状态：测试设计，尚未下载完整测试集、运行恢复实验或产生竞品排名。文中的数量、阈值和周期均为建议验收条件，不是已经达到的结果。

产品定位更新：当前首版改为 Windows/NTFS 误删与清空回收站恢复，见[产品说明](../product-brief.md)。本文通用评估规则继续适用；下面 exFAT/JPEG 的 P0 与 4–6 周专项预算保留为后续研究方案，不代表当前产品开发顺序。

## 1. 要证明的结论

第一项技术目标应写成可以被推翻的假设：**在预先规定的 exFAT、JPEG 碎片化删除场景中，我们从相同输入找回的字节完全一致的原文件，比测试中表现最好的对照工具更多，同时不明显降低普通删除场景的表现。**

“支持更多格式”“发现更多文件”“能看到缩略图”“导出完成”都不能单独证明恢复能力更强。算法效果、设备读取能力、界面操作效率分别测试，最后才评价完整产品。只有通过规定测试，才可以对对应版本、对应样本和对应场景表述优势，不能外推成全市场最高恢复率。

## 3. 测试矩阵

避免一次做所有维度的完全笛卡尔积。首轮只展开标为 P0 的组合；其他组合是独立扩展套件，未测项目明确记为“未测”。

| 维度 | P0：第一项立项 | 后续覆盖 |
| --- | --- | --- |
| 文件系统 | exFAT；FAT32 作为普通删除回归对照 | NTFS，再按产品平台增加 APFS、ext4；版本、簇大小、分区偏移均记录 |
| 文件内容 | 完整原始 JPEG；含/不含 EXIF 缩略图；不同图像尺寸与编码来源 | PNG、HEIC、选定相机 RAW；MP4/MOV 按编码器、codec、容器结构分别建集；ZIP/OOXML/PDF |
| 删除目标 | 预先列出的删除文件，与未删除文件、缩略图、系统文件分开 | 清空回收站、目录删除、目录元数据损坏 |
| 布局 | 连续；2 段顺序碎片；2 段乱序碎片；碎片间填充其他有效文件 | 3 段以上、嵌套、交织、非簇对齐；均保留真实字节布局 |
| 故障 | 删除后目录项/分配信息残留程度不同；目标数据未覆盖 | 快速格式化、分区表丢失、已知范围部分覆盖、头部/尾部缺失、整文件覆盖阴性对照 |
| 容量 | 小型可诊断镜像 + 32/128 GiB 稀疏度可控的性能镜像 | 更大容量、海量文件、超大单文件；稀疏文件不能与实际全盘读取性能混算 |
| 输入 | 未压缩 raw 镜像，通过文件接口或只读虚拟块设备访问 | 真 SD 卡/U 盘、机械硬盘、SSD，各自独立报告；压缩镜像、分卷镜像另测 |
| 错误处理 | 镜像不可读、输出满盘、取消、进程退出、损坏格式 | 实际设备断连；确定性读错误注入、超时/重试预算；坏盘采集另做验证 |

两个场景尤其不能合并：

- **元数据仍在**与**只能依据内容 carving**分开。前者可利用文件簇位置；后者用于验证我们是否真的能重组内容。仅赢前者，不能宣称碎片 carving 更强。
- **逻辑镜像测试**与**设备行为测试**分开。把文件删除后的 raw 镜像保存在 SSD 上，不等于测试 SSD 删除恢复。TRIM/UNMAP 涉及主机与设备的释放通知，设备接收后可处理相应区域；静态镜像不会复现控制器后续行为。[Microsoft TRIM/UNMAP 说明](https://learn.microsoft.com/en-us/windows/compatibility/new-api-allows-apps-to-send-trim-and-unmap-hints)

真实 SSD/闪存实验须用专用可丢弃介质，记录设备型号、固件、接口桥、OS、文件系统、删除/格式化方式、TRIM 状态、断电及采集时间线。同一介质上的试验有时间效应，不能按工具轮流扫描后直接比较。算法比较使用同一时刻采集的冻结镜像；真实采集表现另用分组、重复和随机顺序评价。不要由“TRIM 已启用”推断每个目标块均已清理，也不要因一次读回成功承诺该设备之后仍可恢复。

## 4. 建立可信的标准答案

在故障注入前生成 `originals-manifest.jsonl`，每个目标至少保存：

```json
{
  "sample_id": "capture-001-photo-007",
  "split": "holdout",
  "original_sha256": "<64 hex characters>",
  "byte_length": 1234567,
  "original_path": "/DCIM/100CAM/IMG_0007.JPG",
  "role": "deleted_target",
  "family_id": "capture-session-001",
  "device_encoder_profile": "<device/firmware/encoding settings>",
  "embedded_children": ["<thumbnail sample id, if applicable>"],
  "timestamps_raw": {"creation": "<raw value>", "modification": "<raw value>"}
}
```

另存 `case-manifest.json`：文件系统参数、每个原件的有序 extent（镜像偏移、文件内偏移、长度）、故障操作日志、覆盖区间、故障后每个目标尚存字节区间、输入镜像 SHA-256、创建工具版本、随机种子、是否合成布局。真机照片应来自自有或有测试权的文件；实际用户恢复案例仅在得到明确授权并完成必要处理后引入。

执行规则：

1. 原件、标准答案与故障后的镜像分开保存。被测恢复进程只能读故障后镜像；验证器在恢复完成后才取得标准答案，避免意外“恢复”出备份中的原件。
2. 文件系统生成必须刷新并卸载后取证，检查文件数据确已落盘、目标布局确已形成。不能认为“创建→删除”的脚本一定留下了想测的数据。
3. 普通删除与快速格式化先按 OS/设备正常操作生成，再取镜像。人工修改布局用于可控算法试验，明确标为合成；真实相机生成/删除的验证单独列出。
4. 扫描前后验证冻结输入的哈希。记录工具打开方式；虚拟盘以块层只读暴露，防止自动挂载或工具写入。日志、预览缓存、输出、数据库均放在独立目标存储。
5. 零填充块、常见文件头、重复编码块可能在多个文件出现；块级相似不能独自证明归属。以完整文件 SHA-256 判定 exact，以已知 extent/字节映射定位部分恢复；模糊归属标为不确定。

## 5. 结果分类与指标

结果要建立“一份原件—多个候选输出”的对应关系。每份目标在主指标里最多计一次，优先 exact，再记录其他可用候选。原图、内嵌缩略图、预览图、重复文件、当前仍存在的文件分别统计；恢复一张原图和它的 3 个缩略图，主指标仍最多算 1 个目标成功。

| 分类 | 判定方法 | 是否计入完整原件恢复 |
| --- | --- | --- |
| Exact bytes | 输出长度、SHA-256 与故障前原件一致；需要时逐字节复核 | 是 |
| Partial | 只有部分原始内容，明确记录正确区间、缺失和异源字节 | 否；另计有效内容量 |
| Remuxed | 内容流可能完整，但容器被重新封装，整文件哈希不同 | 否；独立评价全部流、时序和内容 |
| Repaired | 重建头、修改结构、补零或其他修复改变文件字节 | 否；保留派生关系并测量实际可用内容 |
| Invalid / mixed | 无法解析，或混入其他文件/填充/错误顺序的数据 | 否；预览偶尔成功也不改变分类 |
| Unknown | 不能可靠关联到原件或未完成校验 | 否；不强行当成失败原件或成功原件 |

这些是原始字节与处理方式的分类，另设独立的可用性字段：`fully_decodable`（可完整解码）、`partially_usable`（部分可用）、`unusable`。Remuxed 和 Repaired 文件可能有很高的用户价值，哈希不同不能直接等同于无价值；但可完整解码也可能只是损坏内容经过重编码后的结果，不能独自证明原内容完整。

对于媒体，校验采用受限环境中的完整解析/解码，记录解码器版本。图片比较全分辨率内容，视频比较全时段帧、音轨与时序，文档检查内部结构及内容；只打开第一帧、能显示缩略图、仅文件头正确都不足以证明完整。对于容器重建的视频，增加独立的“原有效载荷完整保留”判定：按已知原件比较各轨道 sample/payload、顺序、时间戳、持续时间及缺口，不能只看视频总时长或 remux 成功退出。该项可以证明内容恢复的另一种优势，但不能计入 bit-exact。若以后加入生成式补全，必须独立标为生成内容，不计入恢复出的原始信息。

核心统计：

- **整体 exact 恢复率** = 找回 exact 输出的删除目标数 / 所有预先登记的删除目标数。部分覆盖目标仍在分母中，按故障分层展示。
- **完整数据尚存组的 exact 恢复率** = 该组找回 exact 的目标数 / 故障后全部原始字节仍存在于测试输入中的删除目标数。它衡量算法利用现存信息的能力；不因为某工具不支持格式就缩小分母。
- **输出正确性**：报告每个目标的错误拼接次数、无法归属候选数、无效候选比例。另记录厂商界面原始状态；“导出完成”不被我们擅自解释为“原件完整”。
- **错误成功率** = 被产品明确标为“完整/无损”的候选中，验证为不完整或混入异源数据的数量 / 此类明确完整声明的候选数量。若产品没有这种声明，记为不适用；“格式校验通过”与“原件一致”分别评价。没有标准答案的生产环境不能显示哈希验证原件一致。
- **元数据完整度**：在基准确实保留该字段的目标组中，分别计名称、路径、时间等字段的正确比例，并同时报告“正确内容且路径正确”的目标数。时间须按文件系统精度、时区语义校验，不能拿输出创建时间当原始时间。
- **冗余负担**：每个找回目标对应的重复候选数；缩略图误当原图数；用户需要查看的无效候选数量。不能通过删除所有可疑输出来提高正确性却隐去召回下降。
- **时间与资源**：到首个 exact 导出文件的时间、完成扫描时间、导出时间、完整验证时间、总历时；读取字节数/请求数、输出/临时空间、峰值内存、CPU 时间。速度须与相同时间点已恢复的 exact 数量一起看。
- **操作成本**：从选源到找到指定原图的成功比例、中位耗时、点击数、权限提示次数、误选源/目标次数。初测可用 8–12 位新用户发现问题，不能把这样的探索样本当成已证实的大众用户结论。

## 6. 公平比较与可复现流程

对照至少包含一个免费底线（PhotoRec）和两种面向目标场景的成熟产品。专业对照从 DMDE、UFS Explorer、R-Studio 中选择至少一款，消费者产品从实际支持目标场景的产品中选择。视频专项再纳入 Disk Drill Advanced Camera Recovery 等适用专项模式；不能只比较工具的基础扫描而漏掉适用的高级模式。Scalpel 等实验引擎可作研究对照，不能代替成熟产品对照。

具体版本、版本下载日、build、平台、授权档次、支持接口由实验开始时冻结；付费功能用合法可导出的授权验证。试用版只能预览或有导出额度时，该项目标记“受授权限制、未验证”，不能计成算法失败，也不能因此宣布胜出。

每工具设置两条独立跑道：

- **默认体验**：按官方推荐的普通用户流程完整运行。
- **最佳公开配置**：按官方说明启用适用的深入扫描、碎片恢复、已知文件类型或相机专项模式。在开发/调参集上完成配置选择并冻结；不要看完保留集答案后逐文件调整。PhotoRec 如有适用于 JPEG 的额外碎片/暴力搜索设置，也应纳入相应配置记录。

同一算法比较中使用完全相同的原始输入字节、可见空间范围、目标格式范围和输出设备。支持镜像文件的直接打开；只支持块设备的通过只读虚拟块设备暴露同一镜像，记录适配开销；必须依赖实体设备的功能列入另一套试验。跨 OS 结果分组，不能把不同系统/不同输入介质的扫描时间混排。

建议每个性能条件重复 3 次、随机工具顺序；规定冷/热缓存条件并记录实际控制程度。明确比较“扫描+保存”还是“扫描+预览+导出”，不能拿一款的完整流程对另一款只发现候选的时间。工具崩溃、超时、拒绝输入保留为结果；若重试，所有工具享有相同预定预算。

公开集仅用于开发和回归。自建样本按原始拍摄/编码会话、设备来源、近重复内容族划分为开发、调参、保留集；同一照片换名、转码或反复放到不同镜像，不成为独立原件。保留集在实现与配置冻结后运行一次，若看过答案再改算法，这批数据转入开发集，下次结论需要新的保留集。

报告先按场景显示 exact 的分子/分母，再给预先规定权重的宏平均；文件总量平均仅作补充。比较使用相同目标上的配对差值，置信区间按独立镜像/生成会话分组重采样，不能把同一图片的数十种变体当成数十个独立证据。小样本只报告原始结果和不确定性，不强行宣称显著领先。

一次运行的建议交付物：`run.json`（版本/配置/环境/预算）、`input-hashes.json`、原始日志、导出目录、`outputs.jsonl`（候选哈希/归属/分类）、`per-target.jsonl`（一目标一行）、`metrics.json` 和人工复核争议清单。工具代码、样本生成器和评估器分别版本化；不能只保存最终百分比。

## 7. 推荐首个试验立项

**立项：exFAT 上目标字节仍完整保留、残留分配信息不足的两段 JPEG 恢复。** 目标是验证“文件系统残留信息 + JPEG 结构约束 + 有界片段组合 + 完整解码校验”能否提高 exact 恢复；不先假定任何竞品没有这项能力。

建议配置：收集至少 300 个独立原件，覆盖至少 3 类设备/编码来源，按会话分组 60% 开发、20% 调参、20% 保留。分别构造普通连续删除、两段碎片但分配信息可用、两段碎片且部分分配信息缺失三组；覆盖顺序/乱序、多种间隔长度和真实文件填充。另设少量局部覆盖阴性/部分恢复对照，防止错误拼接被当完整。

保留集至少 60 个独立原件、30 个独立创建/损坏会话；若实际只能拿到更小规模，降级为探索试验。合成条件通过后，再补独立设备生成的真实删除镜像。旧公共集保持回归，但不参与主优势阈值。

建议 4–6 周形成一次 go/no-go 证据包，这是研发预算假设：

1. 第 1–2 周固定输入、标准答案和对照配置，先跑竞品基线，逐个检查失败原因。
2. 第 3–4 周只为可归因的失败开发有限范围算法，同时保存旧行为做消融比较：仅 PhotoRec、仅元数据、仅内容拼接、组合模式。
3. 第 5–6 周冻结实现，运行保留集、争议复核和真实设备生成镜像验证，交付逐目标结果。

**建议通过标准（均非现有成绩）：**

- 在预注册专项保留集上，相比其中最好的对照，exact 恢复率提高至少 **10 个百分点**；配对、按会话分组的差值 95% 置信区间下界大于 0。
- 连续删除回归组 exact 恢复率下降不超过 **1 个百分点**，公开回归用例没有未解释的新损坏/错误拼接。
- 明确宣称完整的输出中，观察到的错误成功率不高于 **1%**，且没有已知未修复的异源拼接仍被声明完整。报告样本量与区间，零次观察不等于真实错误率为零。
- 总历时不超过最强对照的 **2 倍**；同时给出固定时间预算下的 exact 曲线。如果只是用更多算力换回更多文件，按该条件如实表述。
- 单个机型、同一拍摄会话或某种人工填充模式不能解释全部增益；真实设备生成的冻结镜像必须出现同方向改善，否则只称“合成测试通过”。

**终止或转向条件：**

- 最强对照在目标未覆盖组已接近满分，例如 ≥95%，没有足够改进空间：停止以此场景做主要技术卖点，重新选更具体故障。
- 失败主要由目标数据已覆盖/清理造成：停止声称能靠恢复算法补回原字节，改为部分恢复或故障诊断问题。
- 优势来自缩略图刷量、提前看标准答案、只挑一个来源、付费版本未解锁或额外时间预算：该轮胜出结论作废，修正实验再评估。
- 到冻结日期仍不能改善开发集上的可归因失败，或保留集没有稳定增益：不扩大专项引擎投资。可继续做免费易用工具，但不能把界面优势包装为恢复技术领先。
- 发生修改源输入、无法追溯的输出、稳定错误拼接或无界资源耗尽：暂停进入真实用户设备阶段，先解决该类缺陷。

这个试验首先回答“我们是否能在一类具体故障中增加完整原件数量”。通过之后，再决定扩展到 JPEG 多段碎片、选定相机 RAW 或 MP4/MOV；不提前把尚未验证的格式和故障写进能力承诺。
